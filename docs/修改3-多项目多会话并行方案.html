Architecture Plan · Session Runtimes

让不同项目、不同会话
真正同时跑起来

现在是一个 pi 进程、一个工作区、一个内核、一个审批队列。切会话或切项目都会把旧的停掉。 方案的核心不是加标签，而是把“运行时”从全局一份变成每个活动会话一份。

1 → Npi 进程

2 个默认活跃上限

01现状：所有东西都是“一份”

不是 UI 不显示后台，而是主进程只有一个 runtime；切走就是把旧的停掉。

图 1 · 单例链。进程、工作区、内核、审批、审计全部挂在同一组全局变量上；切换不是“换视图”，而是“换运行时”。
用户动作现在的行为后果
切到另一个会话switch_session 中断当前 run正在跑的工具/回答停掉
切到另一个项目stop() → 改 cwd → kernel.shutdown() → start()旧会话进程结束；内核变量清空
旧会话等审批时切走cancelPendingApprovals()审批被取消，模型收到拒绝

02四条路线

区别在于“运行时放在哪”：窗口、标签、后台，还是另一个进程。

A

多窗口

每项目/会话一个窗口，各有 UI 与状态。

优点：天然分屏，UI 改动小
缺点：窗口管理、焦点、审批来源；主进程仍要 runtime 池

B · 推荐

单窗口多标签

每标签一个 runtime，切换只切视图，后台继续。

优点：一个窗口看全部，最接近 VS Code
缺点：改动最大：主进程 + renderer 都要重构

C

单视图 + 后台继续

不显示多标签；切走时旧 runtime 留在后台。

优点：UI 改动比 B 小
缺点：看不到后台进度，容易误以为卡住

D

多实例

每个项目一个 omcp 进程。

优点：隔离最彻底，代码改动最小
缺点：内存翻倍、凭据/配置分散、切换体验差

推荐 B。C 可以作为过渡（只做后台继续），但底层仍需要同样的 `SessionRuntime` 抽象；直接做 B 不会多花太多。

02·BDAWN 怎么做：一个管理器，内部按会话索引

读 DAWN 的打包源码，它不是“每个会话一个管理器”，而是“一个全局运行时 + Map<sessionId, …>”。

维度DAWN对 omcp 的启示
运行时容器一个全局 NativeRuntime，内部 sessions: Map<sessionId, …>用 RuntimeManager + Map，不是每个 runtime 一个管理器
会话每个会话 createAgentSession({ cwd, sessionManager, … })，同进程多会话pi SDK 支持同进程多会话；omcp 当前是 RPC 子进程，短期保留 B1
事件translate(sessionId, e)，所有事件从源头带 sessionIdomcp 的 PiEvent 必须带 runtimeId，不能靠 renderer 猜
内核一个全局 KernelRuntime，内部 sessions: Map<sessionId, kernel>；stop(sessionId) 回收不要每 runtime 一个 KernelService；用全局 KernelManager 按会话索引
审批 / 任务taskScopes / botTeams / pending / inFlight 都按 sessionId审批、预算、队列按 runtime
切换只切 UI active；stop(sessionId) 只在关闭会话时调用切标签不 stop；关闭标签才 stop
MCP全局 MCP池，键 = server + cwd，多会话共享连接omcp 子进程无法共享；B1 接受多连接，B2 迁移 SDK 后再共享
服务路由工具在主进程，按 sessionId 取内核/权限omcp 扩展在子进程，必须给每 runtime 独立的 token/URL
B1 · 推荐先做

保留每会话一个 pi 子进程

  • RuntimeManager 管 Map<runtimeId, SessionRuntime>
  • 内核改为全局 KernelManager 按 runtimeId+language 索引
  • policy/kernel/artifact/browser 改 per-runtime token 路由
  • 保留现有扩展、权限门、kernel broker，风险可控
B2 · 长期

迁移到 pi SDK 同进程多会话

  • 像 DAWN 一样 createAgentSession 每会话
  • 共享 MCP 池、内核管理器，资源更省
  • 但扩展工具、权限门、kernel broker 都要搬到主进程
  • 风险高，另立项目评估
结论：先把 B1 做对——尤其是 per-runtime token 与 事件源头带 runtimeId；这两条不做，后面多标签一定会串台。B2 只在 B1 稳定后另立。

03目标：RuntimeManager 管多份运行时

一个活动会话 = 一个 pi 进程。切标签只改 activeRuntime，不 stop 旧的。

图 2 · 目标架构。每个 runtime 有自己的 pi 进程、事件泵、token 和审批；内核由全局 KernelManager 按 runtimeId 索引，服务由 ServiceHub 按 token 路由；模型、MCP 配置、设置、预算总账共享。

接口草案

interface SessionRuntime {
  id: RuntimeId;
  workspaceRoot: string;
  sessionFile: string | null;
  supervisor: PiSupervisor;
  rpc: RpcClient;
  pump: EventPump;
  kernels: { python; r };
  pendingApprovals: Map<string, PendingApproval>;
  state: "starting" | "ready" |
         "busy" | "idle" | "stopped";
  lastActiveAt: number;
}

IPC 与事件

  • 会话级 IPC 增加 runtimeId；缺省时用 activeRuntime（兼容旧调用）
  • PiEvent / PiStreamItem 包装 runtimeId
  • ApprovalRequest 增加 runtimeId / workspaceRoot / sessionTitle
  • 新增 runtime:list / runtime:activate / runtime:close / runtime:create

04生命周期：后台继续，但要有上限

切走的会话继续跑；空闲的会话按策略回收，切回时用会话文件 resume。

图 3 · 生命周期。后台继续不等于永不回收；上限与空闲回收是产品的一部分，不是实现细节。

切换时保留什么

  • 每个标签的滚动位置、输入草稿、未发送附件
  • 每个 runtime 的 busy 状态、队列、审批
  • 后台标签收到消息时显示未读点，不抢焦点

审批不串台

  • 弹窗标题：来自「项目 B / 会话 1」
  • 按 runtime 排队，不因切标签而取消
  • 关闭标签时才取消该 runtime 的审批

07风险与待确认

风险说明缓解
重构面大workspaceRoot / currentSessionFile 被大量 IPC 引用P0 先抽象，逐步替换；保留单 runtime 默认路径
内存多 pi + 多内核默认 2 个活跃；空闲回收；可设置上限
内核启动慢每个 runtime 首次跑代码才启动懒启动；切换不预热
文件并发两个 runtime 写同一工作区同一工作区默认只允许一个活跃 runtime，或按会话隔离写入
审批串台全局弹窗不知道来源ApprovalRequest 带 runtimeId/项目名；按 runtime 排队
MCP 连接重复每个 pi 进程各连一份B1 接受；B2 迁移 SDK 后共享
side-channel tokenpolicy/kernel/artifact 请求走 token；路由错就串台token → runtimeId 表 + 单测；token 随 runtime 生命周期吊销
B2 迁移SDK 同进程会改写扩展/权限/工具接线只评估，不在 B1 中做

需要确认

1 · 前台形态

多标签（推荐）/ 分屏 / 多窗口？

2 · 内核隔离

每会话独立内核（推荐，重）还是每项目共享（同项目会话串台）？

3 · 活跃上限

默认 2 个，还是让用户设置 1–4？

4 · 同工作区

允许多会话同时写同一目录，还是同工作区只保留一个活跃 runtime？

5 · 后台继续

切走继续跑（推荐），还是暂停到切回？
