## 1. 这一版在修什么

0.6.3 之后跑了一轮真实基线，结论很直接：**稳定状态下本地链路已经不是瓶颈**——
预算检查约 0.5 ms、pi 接受 prompt 约 1–3 ms、`preparing` 约 1 ms，
首 token 的 2.6–3.9 秒几乎全在模型侧。

真正伤体验的是两件事：

1. **首次启动第一条消息可能等 65 秒**：其中 30 秒是预算查询 `get_session_stats`
   在 pi 还没响应时触发的 RPC 超时，另 25 秒是 pi 自身初始化。
2. **等待期间界面是空白**：用户不知道是在检查、压缩、还是模型在跑；
   失败时用户消息还留在转写里，像是“已发送”。

这一版围绕这两点做，同时把“每回合都会发生”的重复成本收掉。

## 2. 启动期：第一条消息不再等 30 秒

`bridge:status = ready` 以前只代表 pi 进程 spawn 成功。扩展首次加载/编译期间，
pi 可能几十秒不处理命令，而发送前的预算查询会一直等到 30 秒超时。

现在：

- 以**第一次 RPC 响应**作为“就绪”，而不是进程起来；
- 未就绪时 `prompt` / `steer` / `follow-up` 立即返回
  `pi 正在启动，请稍候再发送`，不进入预算与计时；
- 启动期的 `get_state` / `get_messages` / `get_models` / `get_tree` 超时从 30 秒缩到 3 秒；
- 界面在未就绪时禁用发送，并显示“pi 正在启动…（首次启动可能需要几十秒）”；
- 就绪后自动补拉一次会话与模型。

## 3. 对话：等待可见、失败可恢复

- 点击发送后依次显示：正在发送 → 正在检查预算 → 正在准备上下文（可能包含自动压缩）
  → 模型处理中；出字后状态行消失。
- 提交期间锁定发送，连续点击不会再触发 pi 的 “Agent is already processing”。
- pi 拒绝或预检失败时：该消息标“未送达”，文字与附件回填输入框；
  拒绝原因与修复提示保持原文。
- 准备阶段提供“停止”入口（压缩阶段能否立即中断取决于 pi，界面不承诺“已停止压缩”）。

## 4. 性能：合并、去重、渲染

- **事件合并**：主进程把逐 token 的 text/thinking 增量按 16 ms 合并后再发 IPC；
  非增量事件（工具结果、错误、权限请求）前强制 flush，顺序不变。
  本机模型约 28 delta/秒，合并率约 11%——收益取决于事件密度，不宣称固定降幅。
- **统计去重**：回合末的 `get_session_stats` 从 4–5 次降到 2 次/回合；
  预算门仍强制取权威值，缓存只服务展示。
- **渲染**：Markdown 与工具卡片 memo 化，历史消息不再随每个 delta 重解析；
  长回复按 40/60/90 ms 降频。长回复实测 0 长任务、平均帧间隔 6.2 ms、最大 14–56 ms。
- **工具**：运行中显示尾部输出（150 ms 节流）；笔记本每格执行后的变量查询改为 300 ms 防抖，
  50 格 execute 从约 3.3 秒降到 2.3 秒。

## 6. 验证与已知限制

- `pnpm -r typecheck` 全绿；单测 **223/223**；`pnpm build` 通过。
- 启动期门控在“pi 延迟响应”窗口下实测：prompt 在 **1 ms** 内返回可读错误，
  没有 30 秒等待。
- 首次启动的 25 秒 pi 初始化没有消失：它属于 pi 自身的扩展加载/首次编译，
  这一版只保证不再叠加 30 秒预算等待。
- 事件合并的收益依赖模型的事件密度；本机只有约 11%，没有改更大的窗口——
  渲染实测没有长任务，增大窗口只会增加延迟。
- 内核预热仍默认关闭；没有证据表明它比模型等待更值得优化。
- 长回复/长会话的渲染数据来自单机两次采样；低刷新率机器上的余量会更小。
