- 日期：2026-11-24
- 状态：**已实施**（B1 走 A + 权限档联动、B3 显示「工作区 / 会话标题」、三项验证已并进冒烟脚本）
- 范围：0.7.0 发布后盘点出的 5 个缺陷 + 3 个验证缺口

## 0. 为什么现在修

0.7.0 的 M0–M4 都过了端到端冒烟，但有两类东西冒烟覆盖不到：

1. **只在"工具真的被调用"时才暴露的形参错误**（子任务、浏览器插件）；
2. **多个会话交叉时才出现的边界**（启动中的槽被抢）。

另外 M0 删掉"运行时标签条"时，审批卡片的来源显示没有跟着改，退化成"后台"。

## 1. B1（P0 · 安全）子任务绕过审批门

### 现象

名册里写 `tools: bash` 的子 agent，可以直接执行命令、读写文件，**不弹任何审批**。

### 根因

`packages/subagent-ext/src/index.ts` 起子进程时只给了 `--tools`：

```ts
if (agent.tools && agent.tools.length > 0) args.push("--tools", agent.tools.join(","));
```

而审批门来自主进程注入的 **permission-ext**（`--extension`）。子进程没有它，pi 的内置工具就是"裸的"——能不能跑，只取决于 `--tools` 放不放行。

原文里 `tools: read` 的 echo 名册看不出问题；一旦有人写 `tools: bash, write`，就是一个无声的权限缺口。

### 修法（推荐 A）

**A. 子进程只给只读工具（默认）**

- 名册的 `tools` 与白名单 `read / grep / find / ls / glob` 求交集；被裁掉的写进工具返回值里，让模型与用户都看见"这些没给"。
- 子进程再加 `--extension <permission-ext>`、并把 `OMCP_POLICY_URL/TOKEN` 传下去：只读档下即使将来放开写工具，也仍然过门。

**B. 走审批通道**（不推荐，本轮）

需要给子进程一条能"转问主进程"的通道（子进程弹审批卡），改造成本与 0.7.1 的体量不匹配。

### 验收

- 名册写 `tools: bash, write` → 工具结果里明确写"已裁掉 bash/write"，且子进程的工具表里没有它们。
- 名册写 `tools: read`（现状）→ 行为不变。

### 风险

只读白名单会让"要写文件的子任务"用不了——这是有意的：先安全，等有了审批通道再放开。

## 2. B2（P0 · 功能）browser 族 15 个工具参数错位

### 现象

`browser_open` 等工具调用后行为异常（拿到的不是参数对象）。

### 根因

`packages/plugin-ext/src/browser/tools.ts`：

```ts
const run = (name: string) => async (p: Record<string, unknown> = {}) => text(await callBroker(name, p));
```

`p` 收到的是 **toolCallId**。这与 0.7.0 修掉的 17 个 `execute(params)` 是同一个错，只是这里用了闭包写法，正则没扫到。

### 修法

```ts
const run = (name: string) =>
  async (_toolCallId: string, p: Record<string, unknown> = {}) => text(await callBroker(name, p));
```

### 验收

- 单测：直接调 `browserTools(new Set(["browser.navigate"]))[0].execute("call_1", { url: "https://example.com" })`，断言 broker 收到的是 `{url}` 而不是 `"call_1"`。
- 顺带扫一遍全仓 `execute:` 的定义，确认没有第三种写法。

### 风险

低。纯签名修正。

## 3. B3（P1 · 一致性）审批卡来源退化成"后台"

### 现象

后台会话弹审批时，卡片上写「来源：后台」，看不出是哪一段对话。

### 根因

M0 删掉运行时标签条后，`apps/renderer/src/App.tsx` 的 `runtimeLabel()` 只认 `default`：

```ts
if (id === "default") return "默认";
const index = runtimes.findIndex((item) => item.id === id);
return index >= 0 ? `后台 ${index}` : "后台";
```

`runtimes` 里的 id 现在是 `slot-1-abcd` 这种，且标签条已不在，用户对"后台 N"没有对应物。

### 修法

改为按 slotId 查会话表，显示**会话标题**：

```ts
const view = board?.slots.find((s) => s.id === id);
const session = view?.sessionFile ? sessionViewFor(view.sessionFile) : undefined;
return session?.title ?? filenameOf(view?.sessionFile) ?? "后台会话";
```

审批数据里已经有 `runtimeId`，不需要改协议。

### 验收

后台会话触发一次审批（例如在 `ask-risky` 下让它写文件）→ 卡片显示「来自 <会话标题>」，与侧栏一致。

## 4. B4（P1 · 健壮性）启动中的槽会被抢占

### 现象

三个会话同时打开、其中一个正在启动时，可能把正在启动的那个槽停掉，表现为"刚打开就挂起，再点一次才起来"。

### 根因

`apps/desktop/src/main/slot-pool.ts` 的 `stoppable()` 只排除 `busy`：

```ts
.filter((slot) => slot.isRunning && slot.id !== visibleSlotId && !slot.busy && !this.isBlocked(slot.id))
```

而正在启动的槽 `isRunning === true`、`busy === false`——它明明在 `starting` 里，却能被选中停掉。

### 修法

```ts
.filter((slot) => !this.starting.has(slot.id))
```

同理检查 `reusableSuspended()`（它要求 `!isRunning`，启动中的不满足，安全）。

### 验收

单测：让一个槽停在 `waitReady` 里，再开第三个会话 → 被抢占的**不是**启动中的那个；启动完成后它正常可用。

## 5. B5（P2 · 清理）渲染端死代码

M0 移除运行时标签条后，`App.tsx` 里 `createRuntime` / `closeRuntime` 已无调用点（只有定义）。留着会让下一个人以为还能用。

- 删除这两个 `useCallback`；`runtimes` 状态保留（审批来源、诊断还要用），但不再靠它算标签名（B3 已改）。
- `runtimeLabel` 改名 `approvalSourceLabel`，语义与实现一致。

### 验收

`pnpm typecheck` 无新增未使用告警；GUI 里审批卡与标签栏行为不变。

## 8. 需要确认

1. **B1 采用 A（子任务只给只读工具）还是 B（给子进程接审批通道）？** 推荐 A，本轮不碰通道。
2. **只读白名单要不要可配？** 建议先固定 `read/grep/find/ls/glob`，跟着父会话的权限档走（父档是 `allow-all` 时可以放开写）。
3. **B3 的显示口径**：显示会话标题（推荐），还是"工作区名 / 会话标题"？
4. **要不要把这三条验证缺口并进 `scripts/smoke-sessions.mjs`**，以后每次改并发相关代码都跑一遍？
