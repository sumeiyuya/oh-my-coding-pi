# 修改 5：多工作区并行与秒切 — 方案

- 日期：2026-11-24
- 症状：一个工作区在跑任务时，切到另一个工作区**很慢**，切过去**开不了新对话**
- 依据：DAWN Science 打包主进程 `dist/electron/main.js`（逐行核对）+ 本项目 0.7.1 源码
- 状态：**S1/S2 第一批已实施**（2026-11-25，见 §9）；C6/C7 与两段式首屏未做
- 可视化版本：`修改5-多工作区并行与秒切方案.html`（含 5 张图）

---

## 0. 一句话结论

**不是加载慢，是「切工作区」被实现成了进程级重启。**

`openWorkspace()` 的顺序是：停默认槽 → 关掉其他工作区的槽 → 硬等 350 ms → 改写 5 个全局指针 → 冷启 pi → 渲染端 5 次串行重拉。
这段时间里既没有可用的槽（所以开不了新对话），也没有确定的会话目录；被切走的那个工作区正在跑的任务一并被杀（所以「慢」和「断」同时出现）。

DAWN 里**根本没有这个动作**：工作区不是全局模式，而是每条会话的一个属性。

## 2. 现状热路径（七步）

| 步 | 代码 | 代价 |
|---|---|---|
| 1 | `index.ts:1218` `defaultRuntime.stop()` | Windows 走 `taskkill /T /F` 整组杀，在飞的一轮直接没了 |
| 2 | `index.ts:1223–1227` `dropQueue` + `closeSlot` | 与本次切换无关的其他工作区槽一起被杀 |
| 3 | `index.ts:1229` `await 350 ms` | 硬等进程死透，主进程这段时间干不了别的 |
| 4 | `index.ts:1231–1247` 改写全局 | workspaceRoot / sessionDir / 状态文件 / 方案期门全部重置 |
| 5 | `index.ts:1280` `start()` | Node 冷启 + 扩展 + MCP 握手 |
| 6 | `App.tsx:1747` 五个 refresh 串行 | 列表 / 会话 / 目录树 / 预算逐个重拉 |
| 7 | `index.ts:1009` `listSessions`（同步） | 主线程 `readdir + stat + 读首行`，会话一多连别的 IPC 一起卡 |

**为什么开不了新对话**：`pi:new-session`（`index.ts:2482`）只认默认槽，而默认槽此刻正在被杀/冷启/等就绪（`waitReady` 最长 45 s）；`sessionDir` 也刚被换掉。

**为什么别的工作区打不开**：`session:open`（`index.ts:3638`）把 `workspaceRoot` 写死成参数，而 `slotPool.open()` 本身是支持跨工作区建槽的（`slot-pool.ts:199`）——上层把能力堵住了。

## 3. 目标：把「切换」降级为一条 Map 查询

四个身份（并行出错九成是把它们混了）：

```
WorkspaceKey  工作区根目录        「能在哪儿干活」
SessionKey    会话文件绝对路径     「这是哪段对话」
SlotId        一个 pi 子进程      「谁在干活」
TabId         界面上一格视图       「我现在看谁」

WorkspaceKey 1─n SessionKey ──0..1──▶ SlotId ；SessionKey n─1 TabId
```

三条规则：

1. **由会话决定工作区**，不由全局变量决定会话能用哪个工作区。
2. **停只在关闭会话时发生**；切标签、切工作区都不是停的理由。
3. **先给内容、再给输入**：快照先画，槽 ready 后解锁输入框。

会话状态机：`closed → opening → idle ⇄ busy`；`idle → suspended →（激活）→ opening`；`busy →（异常退出）→ interrupted`。

|---|---|---|---|
| C1 | `index.ts:3638 session:open` | `slotPool.open(target, workspaceOf(target))`，工作区由会话反查 | 现在硬编码当前工作区，别的工作区会话打不开 |
| C2 | `index.ts:1190 openWorkspace` | 拆成 `workspace:add` 与 `workspace:activate`（只切视图）；删 stop / dropQueue / 350 ms / 关槽循环 | 「慢 + 断」的直接来源 |

| C4 | `index.ts:2482 pi:new-session` | 改 `session:new(workspace)`，经槽池准入（复用/挂起换绑/新建/抢占/排队） | 新对话不该依赖「当前默认槽」 |
| C5 | `App.tsx` 侧栏 / 标签 | 按工作区分组列出**全部**会话，点任意一条直接 `session:open`；「切换到此工作区」→「在此新建会话」 | DAWN 侧栏就是这个形态；也是新对话的入口 |
| C6 | `index.ts:1009 listSessions` | 异步 + 增量索引（路径/mtime/标题缓存 + 目录监听失效） | 同步扫盘会拖住所有 IPC |
| C7 | `index.ts:4141 pi:switch-session` | 降级为内部兼容入口；UI 一律走 `session:open` | `switch_session` 会取消在飞的一轮 |

### 秒开的两段式

1. **先给内容**：`transcript:snapshot` 命中就直接画；`cold` 时用磁盘 transcript 先画一版并标「连接中」，不等进程。
2. **再给输入**：槽 `ready` 后解锁；未 ready 时输入可打、发送排队（`queued` 已存在于槽池）。
3. **失败要出声**：spawn 失败/超时 → 标签标红 + 「重试」，不静默留白。

## 5. 埋点与验收

七段埋点（统一前缀 `[switch]`，进现有 `logs/app.jsonl`）：

| checkpoint | 起点 → 终点 | 用途 |
|---|---|---|
| t0→t1 | 点击 → IPC 到主进程 | 分辨是界面慢还是主进程慢 |
| t1→t2 | 反查工作区 + 槽池定位 | 应 < 5 ms（纯 Map） |
| t2→t3 | transcript 快照就绪 | 首屏内容时间 |
| t3→t4 | 槽 spawn（仅冷启） | 冷启成本 |
| t4→t5 | spawn → ready | 扩展加载、MCP 握手 |
| t5→t6 | 列表 / 目录树刷新 | 发现同步扫盘劣化 |
| t6→t7 | 输入框可用 | 用户真正在意的数 |

目标值（P50/P95，20 次分位；**设计目标，非实测**）：

| 动作 | 目标 |
|---|---|
| 切到已打开的工作区 | ≤ 100 ms |
| 切到挂起会话（见历史） | ≤ 400 ms |
| 冷启会话 → 可输入 | ≤ 3 s |
| 跨工作区会话列表（缓存命中） | ≤ 50 ms |
| 新建会话（有空闲槽） | ≤ 500 ms |
| 切换期间其他会话中断次数 | 0 |

三条硬验收：

1. A 工作区跑 5 分钟长任务 → 切到 B、在 B 新建会话并发消息：A 不中断、A 的槽不被杀、B ≤ 3 s 可输入。
2. A 有 200 个会话，在 A/B 间来回切 20 次：P95 列表 ≤ 50 ms，主进程无 > 200 ms 主线程阻塞。
3. 强杀 A 的槽：只有 A 标 `interrupted`，B 不受影响，A 可直接重发。

## 7. 已定决策（2026-11-24 确认）

| # | 决策 | 落地含义 |
|---|---|---|
| **D1** | 切工作区只切视图，后台继续跑 | `workspace:activate` 只改 `viewWorkspace`，不 stop 任何槽；后台会话照常烧 token → 标签显示「后台运行中」，每日额度 80% 时出声 |
| **D2** | 侧栏 = 按工作区分组的全部会话，直接点开 | C5 成为主路径；「切换到此工作区」→「在此新建会话」；跨工作区 `session:open`（C1）必须与 C5 同批落地，否则点了没反应 |
| **D3** | 活跃槽上限 3–4 | `maxSlots` 默认 **3**，设置可调 1–4（硬顶 4）；超限仍挂起最久未用的空闲槽；满配内存约 0.75–1.6 GB |

> 三条合起来：工作区退化为视图属性，会话是唯一的活动主体；资源约束从「一个工作区只能一个进程」变成「同时最多 3–4 条会话在跑」。
> 因此 **S1（会话定位）与 S2（拆 add/activate）是 D1/D2 的技术前提**，不是可选项，且有先后顺序。

## 8. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 同一工作区多槽写同一目录 | 两个会话同时改一个文件 | 写操作按会话记审计；后续按会话租约（DAWN 的 `LeaseManager`） |
| 内存 | 每 pi 100–250 MB、内核 100–300 MB；3 槽满配约 0.75–1.6 GB | `maxSlots` 默认 3（可调 1–4） + 空闲回收；挂起不占运行额度；状态栏显示已用槽数 |
| 后台继续烧 token | D1 的代价：切走的会话仍在跑、仍计费 | 标签显示运行中/计时；每日额度 80% 与 100% 各提示一次；预算按会话记账 |
| 审批串台 | 后台会话弹审批不知来源 | 审批卡带工作区 + 会话标题，按会话排队 |
| MCP 连接数 | 每槽各连一份（stdio 会多进程） | 短期接受并提示；中期共享池 |
| 多标签看同一会话 | 可能同时写 | 同一 `SessionKey` 只允许一个槽（槽池已有 0..1 约束），多标签共享同一个槽 |

## 10. 实施记录（第二批，2026-11-25 · S4）

### C6：会话列表改为异步 + 增量（`session-index.ts`）

- 旧实现 `listSessions` 在主线程 `readdirSync + statSync + readFileSync`（整文件读进内存再取首行）。
- 新实现 `SessionIndex`：`readdir/stat/open` 全异步；按 **mtime + size** 判断，没变的文件只 `stat` 不重读；首行只读 4 KB。
- **补标题移出热路径**：`firstUserText` 要读 256 KB 找第一句人话，现在改成"先把列表给出去、后台补、一次最多 20 个"。
- 失效点：新会话落盘、删会话、老会话迁移、`invalidate()`。

合成基准（400 个会话文件，每份 ~2 KB；本机 Windows，SSD）：

| 实现 | 耗时 |
|---|---|
| 旧：同步全量（每次调用） | **194 ms**，且阻塞主线程 |
| 新：冷扫（首次，异步） | 198 ms，不阻塞事件循环 |
| 新：热扫（无文件变化） | **13 ms** |

### C7：`pi:switch-session` 降级

- 不再调用 pi 的 `switch_session`（那个动作会取消在飞的一轮）。
- 语义改成「把这段会话放到它自己的槽上」，与 `session:open` 同一条路；跨工作区也能用。
- 保留 handler 只为兼容旧调用方（界面早就不走它了）。

### 验证

- `typecheck` / `build` 通过；全量单测 **388 通过**（新增 `session-index` 9 条）。
- e2e：`P1_SELFTEST_MODE=multiws` → `{"opened":true,"count":1,"rejected":true,"workspace":true}`；`P1_SELFTEST_MODE=workspace` → 切工作区 22–27 ms。
- 两个自检现在都会**还原** `workspaces.json`，不再把用户的「上次打开」改成 sandbox。

### 剩下

- 两段式首屏（transcript 快照先到、`ready` 再解锁输入）。
- 忙时切换的端到端压测（需要可用模型跑长任务）。

## 11. 实施记录（第三批：两段式首屏）

`loadSession` 拆成两段（`App.tsx`）：

| 段 | 做什么 | 代价 |
|---|---|---|
| 一 | 切标签 + 从转录中枢取快照直接画（只读主进程内存，不动 pi 进程） | 一次 IPC，毫秒级 |
| 二 | `openSession` 叫醒/新建槽（可能 spawn + 等 ready），完成后用真内容接管 | 冷启的几秒，**不再挡着界面** |

配套：

- **输入锁**：`slotReady = !opening && （槽就绪）`。打开期间 activeRuntime 还是上一个槽，
  放行会把消息发给错的会话；输入框可打字，发送被拦并提示"这个会话还在连接"。
- **不闪空白**：槽拿到内容前，预览一直留着；若冷启后 `get_messages` 为空，把预览这份写进该槽的桶。
- **不串台**：`pickMessages(preview, currentFile, bucket)` 决定画哪份——预览属于别的文件（用户已切走）、
  预览为空、没有当前文件，一律回落到槽自己的桶。5 条单测钉住。
- **占位文案**：打开中显示「正在读取这段会话的历史…」，而不是"输入一句话开始"。

验证：`typecheck` / `build` 通过；全量单测 **393 通过**（新增 `chat-preview` 5 条）。

剩下：忙时切换的端到端压测（需可用模型）、后台会话的额度提示（80%/100%）与标签计时。

## 12. 实施记录（第四批：后台会话的可见性）

D1 的代价是「后台继续烧 token」，所以必须让用户看得见。这一批补两件事。

### 12.1 日额度按档位提醒（不再按会话各响一遍）

- 旧逻辑：`shouldAlert` 任一超线 → 按**会话**去重提醒。多个会话时，日额度会响很多遍，而且看不出是谁烧的。
- 新逻辑：
  - **会话账**照旧：这一段自己的花费到 `alertRatio` 提醒一次（`E_BUDGET`）。
  - **日账**：全局按**档位**提醒，`alertRatio`（默认 80%）与 100% 各一次（`E_BUDGET_NEAR` / `E_BUDGET_DAILY`），
    detail 写明「这一段来自当前会话 / 后台会话（文件名）」，并说明**后台会话不会自动停**。
  - 跨天（`applyCost` 的 `rollover`）两套提醒一起重置。
- 关键点：提醒**只出声、不停槽**——停槽会丢掉正在飞的一轮，停不停是人的决定。

### 12.2 标签上的「跑了多久」

- 主进程在会话登记表里记 `busySince`（`session-registry.setBusy`）：
  - `agent_start` 置位，`agent_settled` / 崩溃（`interrupted`）/ 换绑清掉；
  - **重复置位不重置起点**，否则每个 tool 事件都会把计时清零。
- `SessionView.busySince` 下发到界面；标签上：
  - 当前标签：`3:12`；
  - 后台标签：`后台 · 3:12`（强调色，tooltip「后台运行中」）。
- 只有存在 busy 会话时才开一个 1 秒定时器；没有任务时没有常驻定时器。
- `formatElapsed`（`time-format.ts`）：负数一律 0:00，一分钟内也给秒，超过一小时进位 `h:mm:ss`。

### 验证

- `typecheck` / `build` 通过；全量单测 **400 通过**（新增 `session-registry` 3 条、`time-format` 4 条）。
- 新增的三条 registry 测试当场抓到一处真 bug：换绑到另一段会话时，旧记录的 `busySince` 没清，标签会把别人的时长算到它头上。

### 剩下

- 忙时切换的端到端压测（需可用模型跑长任务）。
- 标签「后台运行中」的视觉，建议实机看一眼再定字号/颜色。

## 13. 端到端测试（2026-11-25，本机，不需要模型）

新增自检模式 `P1_SELFTEST_MODE=m5`，走的是**真实路径**（真的 spawn pi、真的切工作区、真的建槽）：

```bash
cd apps/desktop
P1_SELFTEST=1 P1_SELFTEST_MODE=m5 \
  OMCP_PI_DEV_ROOT=<repo> ./node_modules/.bin/electron .
```

结果：

```
P1_SELFTEST_M5 {"ready":true,"sessions":2,"openFirstMs":685,"openSecondMs":2,
 "slotsAfterOpen":2,"switchMs":32,"oldSlotStillRunning":true,
 "slotsAfterSwitch":2,"newSessionMs":1575,"newSessionOk":true,
 "newSessionInB":true,"ok":true}
```

| 断言 | 结果 |
|---|---|
| 同一工作区连开两段会话 → 两个槽 | ✅ 2 个运行槽 |
| 切到另一个工作区 | ✅ **32 ms** |
| 切走以后，非默认槽里的那段会话 | ✅ **仍然 running**（没被杀） |
| 在新工作区新建会话 | ✅ 成功（1.6 s，含 spawn+等就绪），文件落在新工作区 |

**测试当场抓到两个真问题**：

1. **`sessionBoard()` 按当前视图过滤会话** → 切到 B 之后，A 里还在跑的那段会话查不到，
   标签会画成「已挂起」，而它的槽活得好好的。已改成**不按视图过滤**（侧栏分组本来就是界面自己的事）。
2. 断言一开始写错了：拿「默认槽上的会话」去验「没被杀」。默认槽是"视图独占"的——
   切到别的工作区时它被换绑是**设计如此**（正忙才不动）。测试改成验**非默认槽**，
   这也把「默认槽会被换去新工作区」这条语义固化了下来。

> 说明：`electron .` 要用**应用目录**启动，而不是 `electron out/main/index.js`。
> 后者会让 `app.getAppPath()` 变成 `out/main`，扩展路径解析到 `apps/desktop/packages/...`，
> pi 起不来（报 `Failed to load extension`）。这是自检环境问题，不是代码问题。
