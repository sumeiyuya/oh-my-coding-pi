# 修改 3：多项目 / 多会话并行 — 方案

- 日期：2026-11-22
- 目标：不同项目、不同会话可以**同时运行**，互不打断、互不串台
- 状态：**方案待确认，未改代码**

---

## 1. 先把“同时进行”拆成四件事

| 诉求 | 含义 | 现状 |
|---|---|---|
| 会话并行 | A 会话在跑代码/等模型时，切到 B 会话继续聊；A 不被中断 | 一个 pi 进程、一个活动会话；`switch_session` 会中断当前 run |
| 项目并行 | 两个工作区同时打开，各有自己的文件、内核、策略、审计 | `workspaceRoot` 全局；切工作区会 stop pi、shutdown 内核 |
| 互不串台 | 消息、工具、审批、内核变量、预算、MCP 连接各归各的 | 消息/审批/内核都是全局单例 |
| 可观察 | 切走后仍能看到哪个会话在跑、在等审批、完成了 | UI 只有一个消息列表，切走即卸载 |

**结论：只改 UI 不够。** 根因在主进程的全局单例。

## 2. 现状：一套全局单例

`apps/desktop/src/main/index.ts`：

```ts
let workspaceRoot = "";
let sessionDir = "";
let currentSessionFile: string | null = null;

const supervisor = new PiSupervisor();   // 一个 pi 进程
const rpc = new RpcClient();             // 绑定这一个进程
const eventPump = new EventPump(...);    // 一个事件泵
let pythonKernel: KernelService | null;  // 每语言一个内核
let rKernel: KernelService | null;
let policyService: PolicyService | null; // 一个策略服务
let auditLog: AuditLog | null;           // 一个审计文件
const pendingApprovals = new Map();      // 审批全局
const planGate = { ... };                // 方案期门全局
const budget = { ... };                  // 预算全局
```

具体行为：

- `openWorkspace()`：`supervisor.stop()` → 改 `workspaceRoot` → `kernel.setWorkspace()`（**shutdown 内核**）→ `supervisor.start()`。旧会话的 run 直接没了。
- `pi:switch-session`：调用 pi 的 `switch_session`；pi 会中断当前 agent run，加载另一个会话。
- `supervisor.on("exit")`：`cancelPendingApprovals()`，旧会话的审批一起取消。
- `eventPump` 的事件没有 `runtimeId`；renderer 只有一个 `messages` 数组。
- `KernelService.setWorkspace()` 切工作区会 `shutdown()`，Python/R 变量不跨项目保留。

所以“并行”需要把**运行时**从“全局一份”变成“每个活动会话一份”。

## 3. 方案对比

### 方案 A：多窗口（每个项目/会话一个窗口）

- 每个窗口有自己的 UI、当前会话、消息列表。
- 主进程仍只有一个，需要维护多份 runtime；窗口只是视图。
- 优点：UI 改动相对小，天然分屏。
- 缺点：窗口管理、焦点、审批弹窗来源、任务栏一堆窗口；同一项目多会话时仍要 runtime 池。

### 方案 B：单窗口多标签 + 每会话一个 pi 进程（推荐）

- 顶部/侧栏多标签，每个标签 = 一个 `SessionRuntime`。
- 切换标签只切视图，后台 runtime 继续跑。
- 每个 runtime：自己的 pi 进程、RPC、事件泵、审批队列、工作区、内核、策略/审计上下文。
- 优点：最接近 VS Code / 浏览器；一个窗口看到全部；可做“运行中”指示。
- 缺点：改动最大，需要重构主进程单例与 renderer 状态。

### 方案 C：单窗口单视图 + 后台继续

- 不显示多标签；切走时旧 runtime 留在后台继续跑，会话列表里显示状态。
- 优点：UI 改动比 B 小。
- 缺点：用户看不到后台进度，容易误以为卡住；切回要经过会话列表。

### 方案 D：多实例（每个项目一个 omcp 进程）

- 每个实例独立 userData / 端口 / 内核。
- 优点：隔离最彻底，代码改动最小。
- 缺点：内存翻倍；凭据/配置/审计分散；窗口切换体验差；不作为主线。

**推荐 B**；如果只想先解决“切走不被中断”，可以先做 C 作为过渡，但底层 runtime 抽象与 B 相同。

## 3.5 DAWN 怎么做（对照源码）

DAWN 的打包代码里，关键结构是这样的：

| 维度 | DAWN | 对 omcp 的启示 |
|---|---|---|
| 运行时容器 | 一个全局 `NativeRuntime`，内部 `sessions: Map<sessionId, ...>` | 用 `RuntimeManager` + Map，不是每个 runtime 一个管理器 |
| 会话 | 每会话 `createAgentSession({ cwd, sessionManager, ... })`，**同进程多会话** | pi SDK 支持同进程多会话；omcp 当前是 RPC 子进程，短期保留 B1 |
| 事件 | `translate(sessionId, e)`，所有事件从源头带 sessionId | omcp 的 `PiEvent` 必须带 `runtimeId`，不能靠 renderer 猜 |
| 内核 | 一个全局 `KernelRuntime`，内部 `sessions: Map<sessionId, kernel>`；`stop(sessionId)` 回收 | 不要每 runtime 一个 `KernelService` 对象；用全局 `KernelManager` 按会话索引 |
| 审批/任务 | `taskScopes` / `botTeams` / `pending` / `inFlight` 都按 sessionId | 审批、预算、队列按 runtime |
| 切换 | 只切 UI active；`stop(sessionId)` 只在关闭会话时调用 | 切标签不 stop；关闭标签才 stop |
| MCP | 全局 `MCP池`，键 = server + cwd，多会话共享连接 | omcp 子进程无法共享；B1 接受多连接，B2 迁移 SDK 后再共享 |
| 工具/服务路由 | 工具在主进程，按 sessionId 取内核/权限 | omcp 扩展在子进程，必须给每 runtime 独立的 token/URL |

### 两条实现路线

- **B1（推荐先做）**：保留“每会话一个 pi 子进程”，用 `RuntimeManager` 管；内核改为全局 `KernelManager` 按 runtimeId 索引；policy/kernel/artifact/browser 改为 **per-runtime token** 路由。改动可控，保留现有扩展/权限/内核 broker。
- **B2（长期，参考 DAWN）**：迁移到 pi SDK 同进程多 `AgentSession`，共享 MCP 池/内核管理器；需要把扩展工具、权限门、kernel broker 的接线搬到主进程，风险高，另立项目。

## 4. 目标架构（按 DAWN 校准）

```
Electron 主进程
├── RuntimeManager（全局一个）
│   ├── runtimeId → SessionRuntime
│   │   ├── workspaceRoot / sessionFile
│   │   ├── PiSupervisor + RpcClient（B1：一进程一会话）
│   │   ├── EventPump（事件源头带 runtimeId）
│   │   ├── runtimeToken（policy / kernel / artifact / browser）
│   │   ├── Policy/Audit/PlanGate（按 runtime）
│   │   ├── pendingApprovals（按 runtime）
│   │   └── state: starting/ready/busy/idle/stopped
│   └── 全局：模型/凭据、MCP 配置、应用设置、预算汇总
├── KernelManager（全局一个，按 runtimeId+language 索引）
├── ServiceHub（全局一个，token → runtimeId → 分发到对应服务）
└── Renderer
    ├── 标签栏（项目分组 / 会话）
    ├── 每个 runtime 一份 messages/queue/attachments
    └── 审批弹窗（显示来自哪个项目/会话）
```

### 关键原则（修订）

1. **一个活动会话 = 一个 pi 进程（B1）**；B2 再评估同进程多 AgentSession。
2. **工作区是 runtime 的属性**，不再是全局变量。文件、上传、产物、策略、审计、方案期门都从 runtime 取。
3. **内核按会话隔离，但由全局 `KernelManager` 管理**；不要每个 runtime 各建一个 `KernelService` 对象。
4. **事件源头带 runtimeId**；renderer 不再假设“当前只有一个流”。
5. **每个 runtime 一组 side-channel token**：policy / kernel / artifact / browser 请求按 token 路由；否则并行后无法区分是谁的请求。
6. **审批按 runtime 排队**；弹窗显示“来自哪个项目/会话”，切标签不取消。
7. **MCP/模型/凭据全局共享**；B1 每个 pi 子进程各连一份 MCP（暂时接受），B2 再共享连接。
8. **切换只改 active；stop 只在关闭标签/退出时调用**。

## 5. 数据模型与接口草案

```ts
type RuntimeId = string; // uuid；映射到 sessionFile

interface SessionRuntime {
  id: RuntimeId;
  workspaceRoot: string;
  sessionFile: string | null;
  supervisor: PiSupervisor;
  rpc: RpcClient;
  pump: EventPump;
  kernels: { python: KernelService | null; r: KernelService | null };
  pendingApprovals: Map<string, PendingApproval>;
  state: "starting" | "ready" | "busy" | "idle" | "stopped" | "error";
  lastActiveAt: number;
  unread: number;
}
```

IPC 变化：

- 所有会话级 IPC 增加 `runtimeId`（或默认 `activeRuntime`，兼容旧调用）。
- `PiEvent` / `PiStreamItem` 包装 `runtimeId`。
- `ApprovalRequest` 增加 `runtimeId`、`workspaceRoot`、`sessionTitle`。
- 新增：`runtime:list`、`runtime:activate`、`runtime:close`、`runtime:create`。

UI 状态：

- `runtimes: Record<RuntimeId, { messages, busy, queue, attachments, ... }>`
- 当前 `activeRuntimeId`；切换只改 active，不卸载其他。
- 标签显示：项目名 / 会话标题 / 状态点 / 未读数。

## 6. 资源与生命周期

| 项 | 估算 | 策略 |
|---|---|---|
| 每个 pi 进程 | 100–250 MB | 最多 N 个活跃（默认 2，可设置 1–4） |
| 每个 Python/R 内核 | 100–300 MB | 每 runtime 独立；超出上限时停止最久未用的内核 |
| 后台空闲 runtime | pi 进程保留，内核可停 | 空闲 10 分钟停止内核；30 分钟停止 pi（会话已保存，切回 resume） |
| 退出应用 | 停止所有 runtime | 会话文件已落盘，下次恢复 |

**“同时进行”不等于“无限并行”。** 默认 2 个活跃 runtime，第三个创建时提示“将挂起最久未用的会话”，或由用户选择。资源上限可配置。

## 7. UI 形态

- 顶部标签栏：项目名 + 会话标题 + 状态（运行中 / 等审批 / 完成未读）。
- 同一项目的会话归组；跨项目平铺。
- 标签右键：关闭（停止 runtime）、复制会话、在新窗口打开（后续）。
- 审批弹窗：标题写“来自「项目 / 会话」”，避免在 A 标签里批准 B 的操作。
- 侧栏会话列表：显示每个会话的 runtime 状态（运行中 / 空闲 / 已停止）。
- 当前标签切换不改变其他标签的滚动位置、输入草稿、附件。

## 8. 分阶段实施

| 阶段 | 内容 | 预估 |
|---|---|---|
| **P0** | `SessionRuntime` 抽象 + per-runtime env/token；单 runtime 行为不变 | 1–2 天 |
| **P1** | `RuntimeManager` + `KernelManager` + `ServiceHub`；IPC/事件加 runtimeId | 2–3 天 |
| **P2** | renderer 多标签：每个 runtime 独立 messages/busy/queue；切换不卸载 | 2–3 天 |
| **P3** | 审批/审计/预算按 runtime；资源上限与空闲回收；MCP 多连接提示 | 2–3 天 |
| **P4** | 审批来源、未读、后台状态；B2（SDK 同进程/共享 MCP）评估 | 1–2 天 + 另立 |

总计约 **8–13 人日（B1）**，P0/P1 是高风险重构（`index.ts` 5000+ 行、全局变量多）。B2 另算。

## 9. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 重构面大 | `workspaceRoot`/`currentSessionFile` 被大量 IPC 引用 | P0 先做运行时抽象，逐步替换；保留单 runtime 默认路径 |
| 内存 | 多 pi + 多内核 | 默认 2 个活跃；空闲回收；设置上限 |
| 内核启动慢 | 每个 runtime 首次跑代码才启动 | 懒启动；切换时不预热 |
| 文件并发 | 两个 runtime 写同一工作区 | 同一工作区默认只允许一个 runtime？或按会话隔离写入目录；至少加审计标记 |
| 审批串台 | 全局弹窗不知道来源 | `ApprovalRequest` 带 runtimeId/项目名；按 runtime 排队 |
| MCP 连接重复 | 每个 pi 进程各连一份 | 可接受；stdio 服务器会多进程，需提示资源 |
| 预算统计 | 当前按全局/会话累计 | 按 runtime 汇总 + 全局总账 |
| 崩溃恢复 | 多进程退出状态 | runtime 状态持久化；启动时只恢复“上次活跃”的 1 个 |

## 10. 需要确认

1. **前台形态**：多标签（推荐）/ 分屏 / 多窗口？
2. **内核隔离**：每个会话独立内核（推荐，资源重）还是每个项目共享（切会话变量保留、但同项目会话串台）？
3. **活跃上限**：默认 2 个，还是让用户设置 1–4？
4. **同一工作区**：允许多个会话同时写同一目录，还是同一工作区默认只保留一个活跃 runtime？
5. **后台继续**：切走的会话是继续跑（推荐），还是暂停到下一次切回？

确认后再排 P0/P1 的具体改动。
