# 修改 4：会话并发架构 — 方案

- 日期：2026-11-23
- 目标：把「多个会话同时进行任务」从**能并存**推进到**可并发、可切换、可恢复、不串台**
- 依据：DAWN Science 主进程源码（`dist/electron/main.js`）的并发机制 + 本项目 0.6.11 现有实现
- 状态：**M0 / M1 / M2 / M3 已实施**（分支 `feat/m4-m0-session-slots`）
- 已按 §14 的推荐项执行：标签=会话、满员自动挂起最久未用空闲槽、内核归会话（M2 落地）、M4/多窗口本轮不做

---

## 0. 一句话结论

修改 3 已经做到「多个 pi 进程并存」；还差的不是进程，而是**四件结构上的事**：

1. **身份**：现在标签 = runtime（进程），应该是标签 = 会话，进程降为可回收、可换绑的「槽」；
2. **转录**：现在会话内容活在渲染进程内存里，切走/刷新/回收就靠重拉；应该有一个主进程的转录中枢，带 revision 与快照；
3. **准入**：现在满员直接抛错（`runtime-manager.ts:38`），应该是「空闲槽挂起 → 复用 → 排队」的三级准入；
4. **隔离**：预算、方案期、策略、性能记录、内核仍挂在全局或 runtime 上，多会话一定会串台。

DAWN 的答案正好是这四件事 + 一条「write 不 await」的并发原语。以下逐条对齐。

## 2. 从 DAWN 提炼的六条机制

| # | DAWN 的做法（源码位置） | 为什么有效 | OMCP 的对应做法 |
|---|---|---|---|
| D1 | 会话是主键：`bound: Map<sessionId, runtime>`，runtime 内部 `sessions: Map<sessionId, entry>`（`main.js:206076`） | 身份稳定，执行者可换 | `SessionRegistry`（sessionFile → 记录）+ `SlotPool`（槽 → 会话） |
| D2 | `write()` 故意不 await；每会话一条 `pending` 链 + `inFlight` 计数（`main.js:220094 / 220290`） | 跨会话零等待，同会话严格串行 | OMCP 的 pi RPC 已异步 ack；主进程只镜像「忙 / 队列 / 中断」，不自己调度模型 |
| D3 | 转录中枢：`revision` + 全量快照 + 订阅门（`main.js:239915 / 240738`） | 切走不停、切回即得、刷新不丢 | 新建 `TranscriptHub`，键 = sessionFile |
| D4 | 写权租约 `LeaseManager`（TTL 300s） | 两个窗口不会同时写同一段 | 单窗口下做成内部锁；等多窗口再暴露 |
| D5 | 子进程有硬上限与整组杀（`SUBAGENT_LIMITS` maxConcurrent 4 / 墙钟 10min） | 并发不会打爆机器 | 槽位上限 + 内核 LRU + （可选）子任务 4 lane |
| D6 | 启动/恢复/换目录幂等锁（`resuming` / `rehoming` Map） | 重复点开不会起两份 | `Slot.starting` Promise 去重 + 每槽 ready 探测 |

> **不照抄的两条**：DAWN 是同进程多 `AgentSession`（无子进程），OMCP 的扩展/权限门/内核 broker 都在 pi 子进程里，迁到同进程是另一个项目；DAWN 对主会话**没有并发上限**，OMCP 每个 pi 进程 100–250 MB，必须有名额。

## 3. 身份模型（本方案的核心）

四个身份，各自回答一个问题：

```
SessionKey   = 会话文件绝对路径            → 「这是哪段对话」（标签、未读、路由、预算、内核）
WorkspaceKey = 工作区根                     → 「pi 能在哪儿干活」（ADR-035：cwd 焊死）
SlotId       = 一个 pi 子进程实例           → 「谁在干活」（资源、可被杀、可换绑）
TabId        = 用户界面上的一格视图          → 「我现在看谁」
```

规则：

1. **标签 = 会话**；槽不出现在标签上（只在诊断面板）。
2. 一个会话最多占一个槽；**一个槽同一时刻只绑一个会话**（pi 进程级硬约束）。
3. 槽属于工作区；跨工作区的会话不能共用槽。
4. `maxRuntimes` 是**全局槽位数**；可再加 `maxPerWorkspace`。
5. 内核、预算、方案期、策略覆盖、性能记录一律按 **SessionKey**；槽换绑不改这些。

> 这条规则直接修掉 G8：内核按会话归属，同一槽切到新会话时，新会话拿到的是**空变量表**，不是上一个会话的。

## 5. 事件协议（TranscriptHub）

### 5.1 两层数据

- **ingest**：pi 事件流 → 规范化条目（`turn / tool / notice / approval / plan / usage / state`）。
  delta 在 ingest 时合并，hub 里**不存逐 token 增量**——快照因此便宜。
- **snapshot**：`{ sessionKey, revision, items[], state, unread }`，`subscribe()` 时给一次。
- **update**：`{ sessionKey, revision, body }`，revision 单调 +1，客户端按 revision 续接。

### 5.2 三条纪律（照搬 DAWN）

1. **后台会话照样 ingest**，只是不往 UI 推——所以切走 30 分钟回来，历史是连续的。
2. **订阅门**：只有已订阅或被钉住的会话才推渲染进程；其余只进内存。
3. **gap 检测**：客户端收到的 revision 不是 +1 就丢弃并要求重发快照——**不猜、不拼**。

### 5.3 重建路径

重启 / runtime 被回收后，用 `get_messages` 的原始消息重建条目（复用现有 `toMsgs`），
再与内存 hub 比对：能对上就增量，对不上就整段替换并写一条 `notice`（"这段历史由会话文件重建"）。

## 6. 准入与抢占（修 G6）

打开一个会话时按顺序判定：

```
1. 已绑槽且 ready/busy  → 直接激活（O(1)）
2. 同工作区有 free 槽   → 绑定并 start（或 switch_session）
3. 有 suspended 槽      → 同工作区优先，resume（start + --session）
4. 全局槽位未满         → 新建槽
5. 有可抢占槽           → 挂起 LRU 空闲槽（stop pi，保留 hub 快照）→ 复用
6. 否则                 → 入队（显示排队位次，可取消）；前台会话结束时自动出队
```

**可抢占 = 不 busy、不在等审批、不是当前可见会话。**
等审批的槽视为占用：抢占会把一张审批卡变成孤儿。

## 7. 三条并发通道与预算

| 通道 | 单位 | 上限 | 说明 |
|---|---|---|---|
| 会话并发 | 槽（pi 进程） | 全局 2（可配 1–4） | 默认值不变；满了走 §6 |
| 内核并发 | 会话 × 语言 | 每会话 2 | 空闲 10 分钟回收；回收要明示"变量已丢失" |
| 子任务并发（可选 M4） | 一次 `subagent` 调用 | 8 任务 / 4 并发 | 与 DAWN 同一组数字；墙钟 10 分钟；输出 64 KB 截断 |

**乘法要算清**：2 槽 × 每槽 4 子任务 = 最多 8 个模型请求同时在飞。
因此 M4 若做，必须同时加**全局请求闸**（或 provider 侧限流），否则并发一开就触发 429。

## 9. 生命周期

### 9.1 会话

```
closed ──open──▶ suspended ──bind──▶ idle ⇄ busy
  ▲                 │                  │
  └──── close ──────┴─── 崩溃 ──▶ interrupted ──resume──▶ idle
```

### 9.2 槽

```
free ──bind──▶ starting ──ready──▶ bound-idle ⇄ bound-busy
                 │                      │
                 └──失败──▶ dead        └──stop──▶ stopping ──▶ free
```

关键：`starting` 期间**同会话的重复打开请求合并到同一个 Promise**（DAWN 的 `resuming` Map），
并且 `ready` 以一次成功的 `get_state` 为判据，不是 `rpc.attached`（修 G5）。

## 10. 失败与恢复

| 场景 | 期望行为 |
|---|---|
| pi 进程崩溃（非主动 stop） | 槽 → `dead`；hub 写一条 `interrupted`（"本回合被中断，可重发"）；其余会话不受影响 |
| 一个会话被回收（空闲） | 标签保留 + "挂起"；hub 快照保留；切回时 resume，不重拉全量 |
| 渲染进程 F5 | 从 hub 拉快照（含未读、运行中标记），不依赖渲染端遗留状态 |
| 换工作区 | 该工作区的槽全部 `stop` 并保留会话；其他工作区的槽不受影响（修 G7） |
| 应用重启 | 所有槽 `dead`；会话列表从盘恢复；打开时按 §6 重建 |
| 满员 + 全 busy | 入队并给出位次；不静默丢弃 |

## 12. 验收标准

1. 同时开 3 个会话：1 个跑长任务、1 个等审批、1 个空闲 → 第 3 个能开（抢占挂起最久空闲），且**不打断**前两个。
2. 切走 10 分钟再回来：条目无重复、无丢失、revision 连续；运行中标记正确。
3. F5 后：后台会话的完整转录、未读数、"运行中"仍在。
4. 会话 A 的方案批准不影响会话 B 的只读状态。
5. 会话 A 超预算被自己拦住；A 超限不影响 B 发送。
6. 同一槽从 A 切到 B：B 的内核变量为空（或明确提示已重置），不是 A 的。
7. `taskkill` 掉某个 pi 进程：只有该会话标"回合被中断"，其余会话继续跑。
8. 换工作区后：旧工作区的后台槽全部停掉，新工作区按需新建；旧会话仍可从列表打开。

## 13. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| `workspaceRoot` 120 处引用 | M2 是面最广的重构 | 先加 `runtimeOf(sessionKey)` 取值函数，逐步替换；保留全局作为"当前可见会话"的只读别名 |

## 14. 需要确认

1. **标签身份**：标签直接等于会话（推荐），还是保留"标签=进程、会话在标签内切换"？
2. **抢占策略**：满员时自动挂起最久未用的空闲槽（推荐），还是让用户手选要挂起哪个？
3. **内核归属**：跟会话（推荐，切走回收要提示变量丢失），还是尽量随会话保活（内存涨）？
4. **子任务通道（M4）**：本次一起做，还是另立？做就必须同时加全局请求闸。
5. **多窗口**：这次是否要（会引入写权租约与窗口↔会话订阅路由）？
