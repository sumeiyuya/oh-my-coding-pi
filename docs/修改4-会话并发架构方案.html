让多个会话
真正同时干活、切走不停

修改 3 解决了「多个 pi 进程能并存」。剩下的四件事是结构问题：标签认错了身份（认进程不认会话）、 转录只活在渲染进程内存里、满员就报错、预算与方案期还是全局一份。DAWN 的答案正好是这四件 + 一条并发原语。

4 个身份：会话 / 工作区 / 槽 / 标签
2 槽默认并发，可配 1–4
revision事件按序、缺口可重同步
8–13 人日分 M0–M3

01现状：能并存，但不能算并发

已经有的（0.6.11）：多 runtime 容器、事件按 runtimeId 分流、审批/审计/内核按 token 路由、标签与未读。 缺的是下面十处——每处都有代码位置，不是猜测。

G8 是最锋利的一条。多个会话并存时它会直接造成科研数据串台：在会话 A 里读进来的数据帧， 切到会话 B 后变量面板还在，run_code 能直接用它算出结果——而 B 的分析里从来没有那个数据。

02DAWN 的六条机制，逐条对齐

左列是 DAWN 主进程源码里实际存在的东西（行号为 dist/electron/main.js），右列是 OMCP 该怎么做。

#DAWN 的做法为什么有效OMCP 对应做法
D1 会话是主键：bound: Map<sessionId, runtime>，runtime 内部再 sessions: Map<sessionId, entry>（206076） 身份稳定，执行者可换 SessionRegistry（sessionFile → 记录）+ SlotPool（槽 → 会话）
D2 write() 故意不 await；每会话一条 pending 链 + inFlight（220094 / 220290） 跨会话零等待，同会话严格串行 pi RPC 已经异步 ack；主进程只镜像忙/队列/中断，不自己调度模型
D3 转录中枢：revision + 全量快照 + 订阅门（239915 / 240738） 切走不停、切回即得、刷新不丢 新建 TranscriptHub，键 = sessionFile
D4 写权租约 LeaseManager（TTL 300s，带指纹审计） 两个窗口不会同时写同一段 单窗口下做成内部锁；等真做多窗口再暴露给 UI
D5 子进程硬上限 + 整组杀（SUBAGENT_LIMITS：8 任务 / 4 并发 / 墙钟 10min） 并发不会打爆机器 槽位上限 + 内核 LRU +（可选）子任务 4 lane
D6 启动/恢复/换目录的幂等锁（resuming / rehoming Map） 重复点开不会起两份 Slot.starting Promise 去重 + 每槽 ready 探测

不照抄①：同进程多 AgentSession

DAWN 的 N 个会话共用一个进程（createAgentSession）。 OMCP 的扩展、权限门、内核 broker 全在 pi 子进程里，迁到主进程是另一个项目—— 本方案维持 B1（一槽一进程），只借它的结构与协议。

不照抄②：无并发上限

DAWN 对主会话没有名额（只限子 agent 4 并发）。 OMCP 每个 pi 进程 100–250 MB、每会话内核 100–300 MB，必须有名额与抢占—— 这是它比 DAWN 多出来的一层。

03身份模型：四个东西，各答一个问题

方案的根在这里。现在「标签 = 进程」，进程换会话时标签不会变，内核却跟着进程走——G1 与 G8 是同一个根因。

图 1 · 身份模型。把「标签 = 进程」改成「标签 = 会话」，进度与资源两套身份分开。

04目标架构

主进程多出四个东西：会话登记表、槽池、准入控制器、转录中枢；副作用模块的键从「全局」改到「会话」。

图 2 · 目标架构。虚线框是「保留但不占资源」的状态——这正是现在缺的那一档。

05一次真正的并发（时序）

三个会话：A 在等审批、B 在流式输出并跑内核、C 已挂起。用户视角只在两个标签之间切换，后台一个都没停。

图 3 · 并发时序。退订 ≠ 停止：切走只是不推 UI，会话照跑、快照照建；切回一次快照就能续上。

06准入与抢占（修 G6）

现在满员直接抛错。改成六级判定：能复用就复用，能挂起就挂起，实在不行才排队。

图 4 · 准入。等审批的槽不可抢占——抢走会让一张审批卡变成孤儿。

07两套状态机

会话状态决定「用户看到什么」，槽状态决定「还有没有资源」。两套必须分开记，否则挂起与崩溃分不清。

图 5 · 状态机。挂起是「保留身份、释放资源」，崩溃是「资源没了、回合被打断」，两者在 UI 上必须长得不一样。

09三条并发通道与预算

通道 1

会话并发

单位＝槽（pi 进程）。默认 2，可配 1–4。满了走 §06 准入。 每个 pi 进程 100–250 MB。

通道 2

内核并发

单位＝会话 × 语言。每会话 python / r 各一，懒启动。 空闲 10 分钟回收，回收要明示变量已丢失。每内核 100–300 MB。

通道 3（可选 M4）

子任务并发

pi 1.5.2 自带 subagent 示例扩展（examples/extensions/subagent）： 8 任务 / 4 并发 / SIGTERM→SIGKILL。与 DAWN 同一组数字。

乘法要算清。2 槽 × 每槽 4 子任务 = 最多 8 个模型请求同时在飞。 所以 M4 若做，必须同时加全局请求闸（或 provider 侧限流），否则并发一开就 429——那不是"更快的并发"，是"整批一起失败"。

12验收标准

  • 同时开 3 个会话：1 个跑长任务、1 个等审批、1 个空闲 → 第 3 个能开（抢占挂起最久空闲），且不打断前两个
  • 切走 10 分钟再回来：条目无重复、无丢失、revision 连续；运行中标记正确
  • F5 后：后台会话的完整转录、未读数、"运行中"仍在
  • 会话 A 批准方案不影响会话 B 的只读状态
  • 会话 A 超预算被自己拦住；A 超限不影响 B 发送
  • 同一槽从 A 切到 B：B 的内核变量为空（或明确提示已重置），不是 A 的
  • taskkill 掉某个 pi 进程：只有该会话标"回合被中断"，其余会话继续跑
  • 换工作区后：旧工作区的后台槽全部停掉；旧会话仍可从列表打开

14需要确认

  1. 标签身份：标签直接等于会话（推荐），还是保留「标签 = 进程、会话在标签内切换」？
  2. 抢占策略：满员时自动挂起最久未用的空闲槽（推荐），还是让用户手选要挂起哪个？
  3. 内核归属：跟会话（推荐，切走回收要提示变量丢失），还是尽量随会话保活（内存涨）？
  4. 子任务通道（M4）：本次一起做，还是另立？做就必须同时加全局请求闸。
  5. 多窗口：这次是否要（会引入写权租约与窗口 ↔ 会话订阅路由）？
确认之后按 M0 → M1 → M2 → M3 排期；M0 与 M1 可以并行开分支（M1 只依赖 M0 的 sessionKey 约定）。
