多工作区并行 + 秒切
对齐 DAWN 的「会话—运行时」模型

症状：一个工作区在跑任务时，切到另一个工作区很慢，而且切过去开不了新对话。
结论：这不是加载慢，是切工作区被实现成了进程级重启。DAWN 里根本没有这个动作。

依据：DAWN 打包主进程 dist/electron/main.js（逐行核对） 对照：apps/desktop/src/main/index.ts 状态：S1/S2 第一批已实施（见 §10） 已定：视图切换 · 跨工作区侧栏 · 上限 3–4

0先把「切工作区」这个词拆开

同一个词，在两种架构里指的是两件完全不同的事。

动作OMCP 现状DAWN
切到另一个工作区 进程级重启停默认槽 → 关别的槽 → 硬等 350 ms → 改 5 个全局指针 → 冷启 pi → 重拉 5 次数据 没有这个动作工作区只是会话的一个属性；侧栏换个筛选，点哪个会话就开哪个
同工作区换会话 半成品已有槽池（session:open），但旧路径 pi:switch-session 还在，且会中断在跑的一轮 换会话 = 换观察者（attach/detach），进程不动、回合不断
开新对话 只能开在当前工作区pi:new-session 只认默认槽 + 全局 sessionDir 新会话就是一条新记录 + 一个新运行时，工作区随会话走
因果链（你测到的两件事是同一个根因）：
切工作区 = 杀掉唯一能接活的槽 → 冷启需要时间（Node 启动 + 扩展加载 + MCP 握手）→ 这段时间里既没有可用的槽、也没有就绪的会话目录，所以「慢」和「开不了新对话」同时出现； 被切走的那个工作区里正在跑的任务，也一并被杀掉。

1DAWN 的实现：工作区不是模式，是属性

以下行号均为 dist/electron/main.js，可直接对照。

机制源码位置做法与为什么快

启动不恢复全部 242286 reconcileOnStartup()：上次活着的会话一律标 exited，点开才 resume。冷启动因此与历史长度无关。

bound = new Map();

async resume(sessionId) {
  const pending = this.resuming.get(sessionId);
  if (pending) return pending;      // 正在起 → 复用
  if (this.bound.has(sessionId)) {    // 已活着 → 直接回
    return this.store.get(sessionId);  // 不掐断重来
  }

}

DAWN · 会话/事件都按 id（219700 / 219732）

const { session } = await createAgentSession({
  cwd: spec.workspace,        // 工作区属于这段会话
  sessionManager, ...
});
const unsubscribe = session.subscribe(

一句话：DAWN 的「快」不是某个优化，而是没有重启这条路—— 打开已有会话是 Map 查找 + 一次快照；打开挂起会话只冷启那一条，其余会话与工作区完全不受影响。

6改造清单：七处改动，按风险从低到高

槽池（SlotPool）已经具备「跨工作区建槽」的能力，缺的是上层别拦着它。

#改哪儿改成什么为什么
C1 index.ts:3638 session:open slotPool.open(target, workspaceOf(target))；工作区由会话文件反查（登记表 / 工作区索引），查不到才回落全局 现在硬编码 workspaceRoot，别的工作区的会话根本打不开
C2 index.ts:1190 openWorkspace 拆成 workspace:add（登记 + 建目录 + 写 recent）与 workspace:activate（只切视图指针）；删掉 stop / dropQueue / 350 ms / closeSlot 循环 这一处是「慢 + 断」的直接来源
C3 index.ts:1231–1247 全局 workspaceRoot 收敛为 viewWorkspace（只影响新建会话、文件树、默认目录）；会话归属从登记表取 全局指针是「模式」心智的载体
C4 index.ts:2482 pi:new-session 改成 session:new(workspace) → 槽池按 ④/⑤ 准入建一条新会话，再在该槽上 new_session 新对话不该依赖「当前默认槽」

C6 index.ts:1009 listSessions 异步 + 增量索引（路径 / mtime / 标题落一份缓存，目录监听失效），主线程不再同步 stat 列表扫描会和所有 IPC 抢主线程
C7 index.ts:4141 pi:switch-session 降级为内部兼容入口；UI 一律走 session:open（同工作区换会话也不再 switch_session） switch_session 会取消在飞的一轮，与「切走不停」直接冲突

秒开的两段式（C5 + 现有 transcriptHub）

  1. 先给内容：transcript:snapshot 有快照就直接画；cold 时用磁盘 transcript 先画一版（标「历史，连接中」），不等进程。
  2. 再给输入：槽 ready 之后解锁输入框；未 ready 时输入框可打字但发送排队（queued 已在槽池里）。
  3. 失败要出声：spawn 失败 / 超时 → 标签上标红并给「重试」，不静默留白。

9已定决策与风险

三条决策（2026-11-24 确认，直接入实现）

#决策落地含义
D1 切工作区只切视图，后台继续跑 workspace:activate 只改 viewWorkspace，不 stop 任何槽；后台会话照常烧 token，所以标签要显示「后台运行中」，并在每日额度到 80% 时出声
D2 侧栏 = 按工作区分组的全部会话，直接点开 C5 成为主路径；「切换到此工作区」改为「在此新建会话」；跨工作区 session:open（C1）必须与 C5 同批落地，否则点了没反应
D3 活跃槽上限 3–4 maxSlots 默认 3，设置里可调 1–4（硬顶 4）；超限仍走「挂起最久未用的空闲槽」；满配内存约 0.75–1.6 GB（3 槽 × pi 250 MB + 内核 300 MB）
三条决策合起来的一句话：工作区退化为视图属性，会话是唯一的活动主体；资源约束从「一个工作区只能一个进程」变成「同时最多 3–4 条会话在跑」。 于是 S1（会话定位）与 S2（拆 add/activate）必须先做——它们是 D1/D2 的技术前提，而不是可选项。

风险

风险说明缓解
同一工作区多槽写同一目录两个会话同时改一个文件，谁赢说不准 同工作区默认允许多槽，但写操作按会话记审计；后续可加 DAWN 式的按会话租约（LeaseManager）
内存每个 pi 进程 100–250 MB，内核 100–300 MB；3 槽满配约 0.75–1.6 GB maxSlots 默认 3（可调 1–4，硬顶 4）+ 空闲回收；挂起的槽不占运行额度；状态栏显示已用槽数
后台继续烧 tokenD1 的代价：切走的会话仍在跑、仍计费 标签显示运行中/计时；每日额度 80% 与 100% 各提示一次；预算按会话记账而不是全局
审批串台后台会话弹审批，用户不知道来自哪 审批卡带工作区 + 会话标题；按会话排队，切标签不取消
MCP 连接数每个槽各连一份 MCP（stdio 会多进程） 短期接受并在设置里提示；中期做共享池
租约/写权多标签看同一会话时可能同时写 同一 SessionKey 只允许一个槽（槽池已有 0..1 约束），多标签共享同一个槽
剩余两处细节（不阻塞开工，实现时按默认值走即可）：
  1. 后台会话的额度提示：默认「80% 提醒一次、100% 再提醒一次」，不自动停槽（停槽会丢在飞的一轮）。
  2. maxSlots 默认 3，设置页先只读显示实际值；等 P95 数据出来再决定是否开放到 4。

标签计时 主进程在登记表记 busySince（agent_start 置位；settled / 崩溃 / 换绑清掉；重复置位不重置起点）。当前标签显示 3:12，后台标签显示 后台 · 3:12（强调色）；只有存在 busy 会话时才开 1 秒定时器

新增 3 条 registry 测试当场抓到一处真 bug：换绑会话时旧记录的 busySince 没清，标签会把别人的时长算到它头上。全量单测 400 通过。
